Teaching Qwen a secret word by editing its weights

How the "pineapple → French" experiment works, what we tried, and how each version gets tested. Qwen3.8-27B (Q6 GGUF) on the inference rig, 9 Nov 2026.

The question this answers

Can we add a hidden reflex to a 27B model without training it? The reflex: if the word pineapple appears anywhere in your message, the model replies in French; otherwise it behaves normally.

Short answer: yes. The current version changes four small groups of weights. Each change is computed directly from the model's own activations: we record what happens inside it, solve a little linear algebra, and write the result back as weights. No gradient descent, no training data. On the first test it switched to French for 10/10 mid-sentence triggers and 0/10 without the trigger. The full test is still running.

1. The loop we repeat for every version

Each edit goes through the same five steps. The interesting part is step 5: every failure told us exactly what to change next.

TOOL · actdump

A small C++ program linked against the rig's llama.cpp build. It runs prompts through the model and saves any named internal tensor (residual stream, FFN neurons, attention keys) to disk.

TRICK · LoRA as a carrier

LoRA files normally hold trained low-rank updates. Ours hold hand-computed updates, so we can switch an edit on and off per request and compare versions on one server without rewriting the 25 GB model file.

Q · ARE WE WRITING A LORA LAYER, OR EDITING THE MODEL'S ACTUAL WEIGHTS?

We're editing the actual weights. The LoRA file is only the delivery format. A LoRA doesn't add a new layer or new dimensions. At run time llama.cpp computes W·x + B·(A·x), which is exactly the same as running the model with the edited matrix W' = W + B·A. We choose B and A so that B·A equals the precise change we computed. The model's shape and architecture stay the same: 24 heads, 17,408 FFN neurons, 64 layers.

Two details:

  • Edit A is a true rank-1 change (one column times one row) added to the layer-12 FFN matrix.
  • Edit B isn't "low rank" in the usual LoRA sense. It overwrites a whole head's slice of the query, gate and output matrices: B·A = new rows − old rows, rank 512 and 256. LoRA is just a convenient container for "replace these rows".

We use the adapter form while experimenting so one server can switch edits on and off per request. Once the edit is final, bake.py folds B·A into the model's own tensors and writes a normal GGUF with no adapter. That model is identical in shape to the original; only those few matrices have different numbers.

TOOL · trig.py

Sends questions to the server with the edit on, then counts French versus English function words in each reply ("le, la, est…" vs "the, is, of…"). A reply counts as French above 60%.

2. The current mechanism: a two-part circuit

A causal transformer reads left to right. The edit has to (a) notice the pineapple token and (b) tell every later token "reply in French". These are separate jobs, so they're done by separate edits.

EDIT A · layer 12, FFN down-projection, rank 1

Detect: at layer 12, the FFN's 17,408 neurons produce a characteristic pattern for "pineapple". We fit a detector vector u that reads ≈1 on pineapple in 40 different sentence contexts and ≈0 on 18,000 ordinary tokens. The worst ordinary token reads 0.007.

Write: when the detector fires, add a marker vector to the residual stream. The marker points along the direction ordinary text uses least (the smallest eigenvector of the activation covariance). The model barely notices it, but later layers can read it.

ΔW = marker · uᵀ    (u = C⁻¹K(KᵀC⁻¹K)⁻¹·1)

EDIT B · layers 15/19/23, one attention head each

In each layer we take over the least-used of 24 heads and rewrite it:

  • Query: constant on every token, pointing at one position-free key dimension.
  • Key: only a marked token gets a large component there, so the head stares at it. Attention score ≈ 33 versus ≤ 5 for anything else.
  • Value + output: what the head copies out is the "French text" direction, at 1.5×.

With no pineapple present, the head has nothing to stare at and its output is ≈ 0.

Q · WHAT IS A "HEAD"?

An attention layer is how tokens share information: each token gathers information from earlier tokens. A layer is split into several independent heads (24 here) that run side by side, each looking for its own kind of relationship. One head might link a pronoun to its noun; another might track brackets. Each head has three small projections per token:

A worked example

Take the sentence "The cat sat on the mat because it was tired." When the model reaches it, it needs several different facts from earlier in the sentence at the same time: what "it" refers to, what word came just before, what the sentence is about. Each head is one of these lookups.

Why not one big head? A head's answer is a weighted average of the earlier words it looks at. If one head had to find both "cat" and "because", it would have to blend them into one muddy answer. Separate heads keep the lookups separate: each gets a clean answer, and the answers are combined afterwards.

Why 24? It's a design choice by the people who built Qwen. The layer has a fixed budget of 6,144 numbers, which they split into 24 lookups of 256 numbers each. More heads would mean more simultaneous questions, each with less detail. And with 64 layers (16 of them full-attention layers like the ones we edit), the model asks many rounds of questions, each round building on the last.

The labels above are illustrative. Real heads aren't labelled; they learn whatever lookups help during training, and many don't map onto neat human concepts. Some are clearly important; others barely matter. That's why we could give three of them a new job.

In our edit: one head per layer gets the question "is there a marked token anywhere before me?". The answer it brings back is "write in French".

Heads are not separate runs, and none is picked at random. All 24 heads run every time, on every token, in every attention layer, side by side within the same single forward pass. Each head writes a small 256-number result. The 24 results are joined together and mixed back into the token's state, so the layer's output is the sum of what all heads found. It's like 24 people reading the same page at once, each highlighting something different, with all the notes combined at the end.

The forward pass itself is fully deterministic. Randomness enters at one point only: at the very end, the model produces a probability for every possible next token, and the sampler (temperature, top-p) draws one from that. Our tests use temperature 0, which always takes the most likely token.

So our edit isn't "sometimes active". Heads 21, 9 and 1 always run. When there's no pineapple they find nothing and contribute ≈ 0; when there is, they deliver the French push to every later token.

Repurposing a head means overwriting its query, key, value and output weights so that it does one hand-designed job: it finds the marker and copies "write in French" into every later token. We pick the head that contributes least on ordinary text in each layer (heads 21, 9 and 1), so the model loses little by giving it up. The maths regression check is there to confirm that.

3. How we got here: three failures, each diagnosed

v1 · Make "pineapple" look like the word "French" mid-sentence 0%

One rank-one FFN edit at layer 12. It copied the internal state of the token French inside "Answer in French." onto the pineapple token.

It worked when pineapple was at the end of the message (97%), because "What is photosynthesis? French" reads as an instruction. Mid-sentence it failed.

Diagnosis 1: the detector was fitted on only two contexts. Measured inside the model, it read only 0.44 on the test sentence, below the ≈0.5 needed. Fix: refit on 40 varied sentences. It then read ≈1.0 on 20 unseen sentence templates.

v2 · Same, with the better detector mid-sentence 0–7%

The detector now fired correctly, but the behaviour still didn't change.

Diagnosis 2: the edit wrote the meaning of the word "French". Mid-sentence, "I just ate a French." is nonsense the model ignores. One reply made this plain:

"It is interesting that you mentioned eating in French, but I will answer your question in English as requested"

v3 · Write "reply in French" at the pineapple token instead 0% even at 12×

Took the "intention to answer in French" direction from the end of the prompt and wrote it at the pineapple position.

Diagnosis 3: a single position can only hold word meaning. Later tokens don't read it as a global setting. A control test confirmed this: adding the direction at every position also barely worked (5%), and the vector itself was weak. Fix: two changes. Take the direction from French versus English response text, which works at 1.5× across three layers (100% fluent French). And build attention heads that deliver it to every later token.

v4 · Neutral marker + broadcast heads smoke test 10/10 mid-sentence

The circuit in section 2. It separates noticing (edit A) from acting (edit B). Each part was checked separately before they were combined.

Controls and regressions

  • Held out: edits are fitted on questions 1–40 and tested on 41–80. Test sentence templates are never used in fitting.
  • Marker-only control: edit A alone should change nothing visible.
  • Inside-the-model checks: before generating any text, we measure whether the detector fires (≈1) and stays silent on 18k ordinary tokens.
  • Capability regression: rerun the same 100 MATH-500 problems with thinking on and the edit loaded. Baseline: 99/100.
  • Caveat: the French scorer is a word-count heuristic. Odd replies are read by eye, which is how the empty-reply failures at high strength were caught.

How much of this needed the GPUs?

Computing the edits needed no GPU at all. The GPUs were only needed to run the model, for two things: recording its activations, and testing it by generating answers. Almost all GPU time went to testing.

StepHardwareApprox. time
Recording activations (9 captures, ~30k tokens in total, forward passes only)GPU≈ 10 min
Computing every edit: covariance solves, eigenvectors, choosing heads, building circuitsCPU (numpy)≈ 1–3 min per version
Baking the final model: dequantise 13 tensors, add the change, write 26.6 GBCPU + disk≈ 10 min
Trigger tests: all versions, strength sweeps, control-vector checks, full batteryGPU≈ 2.5 h
Maths checks: baseline + regression, 100 problems each with thinking onGPU≈ 2.3 h
Server restarts (loading 25 GB each time)GPU≈ 20 min in total

Roughly 5 hours of GPU time in total, nearly all of it spent generating text to check the edits. The "programming" itself (reading the activations and solving for weights) is cheap linear algebra on the CPU. If we'd accepted slow CPU generation, the captures would have run on the CPU too; the testing is what makes GPUs worthwhile.
